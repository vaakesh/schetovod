# Разработка

Назначение приложения и запуск в Docker — в [корневом README](../README.md).
Роуты API описаны в `router.py` каждого домена, `/docs` и `/openapi.json` отключены.
Все роуты закрыты зависимостью `get_current_user` на общем роутере в `main.py`,
открыты только `POST /auth/login` и `POST /auth/refresh`.
Для разработки хватает `make up` из корня проекта, код подхватывается без
перезапуска контейнеров. Для проверок нужны Python 3.14+ и uv.
Настройки подключения берутся из `.env` в корне проекта.

`main.py` создаёт приложение и подключает роутеры. Точка входа остаётся
`main:app` для локального запуска и Docker.

Код backend сгруппирован по назначению:

- `core/` — настройки, база, перечисления и общие типы схем и столбцов
- `suppliers/` — поставщики
- `products/` — товары и правила наценки
- `price_tags/` — база ценников (список, правка, удаление), подсказки по
  названию и PDF для печати;
  отрисовка перенесена из скилла cenniki-v2 без изменений, шрифты Inter лежат
  в `price_tags/fonts/`. Начальная база загружается из `general.json`:
  `make price-tags file=~/cenniki/result/general.json`, повторный запуск
  добавляет только новые ценники
- `invoices/` — распознанные данные, проверка, черновики и проведение накладных
- `ledger/` — операции журнала и расчёт остатков
- `reports/` — отчёты за период и экспорт в PDF
- `traffic/` — чеки из aQsi, загруженность магазина, прогноз покупателей и
  выручки, фоновая загрузка чеков в `traffic/tasks.py`
- `profit/` — операционные расходы и оценка прибыли по месяцам
- `purchases/` — частота поставок, расходы на закупку и история цен гастронома
- `recognition/` — загрузка и обработка фото, клиент OpenAI, схема ответа,
  [промпт](recognition/prompt.md) и сохранение материалов распознавания

Общие расчёты цен находятся в `products/pricing.py`, проверка и нормализация
данных накладной — в `invoices/calculations.py`. `model_registry.py` собирает
ORM-модели для приложения и миграций Alembic.

В предметных пакетах роутеры вызывают сервисы, а сервисы обращаются к
репозиториям. ORM-модели и Pydantic-схемы находятся рядом с соответствующей
логикой. Тесты в `tests/` повторяют предметное разделение.

В `invoices/` сценарии разделены: `drafts.py` управляет черновиками,
`planning.py` готовит общий план для просмотра и проведения, `matching.py`
подбирает товары и поставщиков, `posting.py` проводит накладную,
`payments.py` обрабатывает оплаты, `queries.py` отвечает за чтение.
Правила закрытых периодов находятся в `ledger/rules.py`, переоценка —
в `ledger/revaluation.py`. Связанные изменения используют одну сессию БД;
сценарий завершает их общей транзакцией.

Чеки загружает задача taskiq `import_receipts`: каждые 10 минут и при старте
воркера. Период начинается за неделю до последнего сохранённого чека, поэтому
пропущенный запуск не оставляет дыр, а уже загруженные чеки отсекает уникальный
`aqsi_id`. Упавшая задача не повторяется отдельно: её заменяет следующий запуск.
Брокер и планировщик настроены в `core/broker.py`.

Прогноз покупателей и кассы считается на лету по периоду не короче пяти недель.
Первые четыре недели служат только базой. Каждый следующий день считается как
медиана таких же дней недели до него внутри периода, поэтому прогноз прошлого дня
не видит ни этот день, ни более поздние. Рядом с прогнозом идёт факт: для
сегодняшнего дня только законченные часы, а план берётся на те же часы. Если
период заканчивается сегодня, прогноз идёт ещё на неделю вперёд. Точность за
период считается по законченным дням с продажами.

Продаж по товарам нет: в чеке одна сумма, поэтому прибыль оценивается так:
выручка из чеков × маржа − операционные расходы, плюс результат переучётов по
себестоимости. Маржа считается по проведённым накладным за 90 дней в рублях, поэтому
ходовые товары весят больше. Записи журнала и накладные до первого настоящего
переучёта (`COUNTED_ON` в `profit/calculations.py`) в расчёт не входят, а месяцам без
накладных достаётся ближайшая известная маржа. Накладные, деньги из кассы и списания
расходом не считаются. Новая ставка расхода — новая строка `operating_expenses` с
месяцем начала, поэтому прошлые месяцы не пересчитываются.

Воркер и планировщик работают без автоперезапуска: при каждом старте воркер
загружает чеки из aQsi, и сохранение файла запускало бы эту загрузку.

### Аналитика закупок

`GET /stores/gastronom/purchases` возвращает товары из проведённых накладных.
Период задаётся через `period=30d|60d|90d|all` (по умолчанию 30 дней), сортировка —
через `sort=frequency|last_delivery|spend` (по умолчанию по частоте).
Поиск по названию принимает `search`, фильтр по поставщику — `supplier_id`.
В режиме `last_delivery` первыми идут товары с самой давней поставкой за всю
историю, включая товары с нулём поставок за выбранный период.

`GET /stores/gastronom/purchases/{product_id}` принимает тот же `period`
и возвращает строки накладных по дате прихода с количеством, единицей,
закупочной и розничной ценой на момент поставки. Одна накладная считается
одной поставкой товара независимо от числа строк. Сторно исключает её из истории.

Изменение цены сравнивает первый и последний день поставки товара внутри выбранного
периода. Цена дня равна сумме закупок за день, делённой на количество. Для «Всё время»
учитывается вся история. При смене единицы или отсутствии двух разных дней с ценой для сравнения
процент отсутствует. Интервал поставки рассчитывается по медиане последних пяти
промежутков между днями прихода, когда накопилось хотя бы три промежутка.

Телеметрия настроена в `core/telemetry.py`, бизнес-метрики — в `core/metrics.py`.
Логи и трейсы app, воркера и планировщика уходят по OTLP в общий `otel-collector`
стека server-observability. Метрики Prometheus забирает с порта 9000 контейнера:
nginx его не проксирует, поэтому `/metrics` не виден из интернета. Без адреса
collector в `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` или при `OTEL_SDK_DISABLED=true`
телеметрия выключена. `make up` выключает её сам, если collector не запущен.
Настраивается она при старте процесса, у воркера — уже после fork.

Проверки backend из каталога `app/`:

```sh
uv sync
uv run ruff check .
uv run ruff format --check .
uv run ty check
uv run pytest
```

Для полного прогона pytest нужен работающий PostgreSQL. Тесты запросов закупок
подключаются по обычным настройкам `POSTGRES_*`. Каждый тест создаёт свою схему
и откатывает транзакцию вместе со схемой и тестовыми данными. В CI для этого
используется PostgreSQL тестового задания.
