# Разработка

Назначение приложения и запуск в Docker — в [корневом README](../README.md).
Роуты API описаны в `router.py` каждого домена, `/docs` и `/openapi.json` отключены.
Все роуты закрыты зависимостью `get_current_user` на общем роутере в `main.py`,
открыты только `POST /auth/login` и `POST /auth/refresh`.
Для разработки хватает `make up` из корня проекта, код подхватывается без
перезапуска контейнеров. Для проверок нужны Python 3.14+ и uv.
Настройки подключения берутся из `.env` в корне проекта.

`main.py` создаёт приложение и подключает роутеры. Точка входа остаётся
`main:app` для локального запуска и Docker.

Код backend сгруппирован по назначению:

- `core/` — настройки, база, перечисления и общие типы схем и столбцов
- `suppliers/` — поставщики
- `products/` — товары и правила наценки
- `invoices/` — распознанные данные, проверка, черновики и проведение накладных
- `ledger/` — операции журнала и расчёт остатков
- `reports/` — отчёты за период и экспорт в PDF и XLSX
- `traffic/` — чеки из aQsi, загруженность магазина, прогноз покупателей и
  выручки, фоновая загрузка чеков в `traffic/tasks.py`
- `recognition/` — загрузка и обработка фото, клиент OpenAI, схема ответа,
  [промпт](recognition/prompt.md) и сохранение материалов распознавания

Общие расчёты цен находятся в `products/pricing.py`, проверка и нормализация
данных накладной — в `invoices/calculations.py`. `model_registry.py` собирает
ORM-модели для приложения и миграций Alembic.

В предметных пакетах роутеры вызывают сервисы, а сервисы обращаются к
репозиториям. ORM-модели и Pydantic-схемы находятся рядом с соответствующей
логикой. Тесты в `tests/` повторяют предметное разделение.

В `invoices/` сценарии разделены: `drafts.py` управляет черновиками,
`planning.py` готовит общий план для просмотра и проведения, `matching.py`
подбирает товары и поставщиков, `posting.py` проводит накладную,
`payments.py` обрабатывает оплаты, `queries.py` отвечает за чтение.
Правила закрытых периодов находятся в `ledger/rules.py`, переоценка —
в `ledger/revaluation.py`. Связанные изменения используют одну сессию БД;
сценарий завершает их общей транзакцией.

Чеки загружает задача taskiq `import_receipts`: по понедельникам в 04:00 и при
старте воркера. Период начинается за неделю до последнего сохранённого чека,
поэтому пропущенный запуск не оставляет дыр, а уже загруженные чеки отсекает
уникальный `aqsi_id`. Упавшая задача повторяется до 8 раз с растущей паузой,
паузы хранятся в Redis и переживают перезапуск. Брокер и планировщик
настроены в `core/broker.py`.

Воркер и планировщик работают без автоперезапуска: при каждом старте воркер
загружает чеки из aQsi, и сохранение файла запускало бы эту загрузку.

Проверки backend из каталога `app/`:

```sh
uv sync
uv run ruff check .
uv run ruff format --check .
uv run ty check
uv run pytest
```
